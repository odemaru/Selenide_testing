# UI-тесты магазина Toolshop

[![tests](https://github.com/odemaru/Selenide_testing/actions/workflows/tests.yml/badge.svg)](https://github.com/odemaru/Selenide_testing/actions/workflows/tests.yml)

Автотесты веб-интерфейса демо-магазина Toolshop: витрина, регистрация, вход,
корзина и оформление заказа. Java, Selenide, JUnit 5, Allure.

**Стенд:** https://practicesoftwaretesting.com

> Парный проект к [тестированию API 2GIS](https://github.com/odemaru/2gis_testing).
> Тот проверяет один метод вглубь, этот — пользовательские сценарии вширь,
> и решает задачи, которых у API-тестов нет: ожидания, изоляция состояния,
> параллельный прогон браузеров.

## Запуск

Нужен JDK 21 и установленный Chrome. Maven ставить не требуется: в проекте
лежит wrapper.

```bash
./mvnw test
```

Другие варианты:

```bash
./mvnw test -Dheadless=false            # с открытым окном браузера
./mvnw test -Dtest=CartStateTest        # один класс
./mvnw test -Dbrowser=firefox           # другой браузер, см. оговорку ниже
./mvnw test -Dthreads=1                 # без параллельного прогона
```

Набор проверен на Chrome. Выбор браузера вынесен в настройку, и Selenide
берёт драйвер сам, но прогон на Firefox я не гонял — заявлять его рабочим
не буду.

Отчёт Allure после прогона:

```bash
./mvnw allure:serve
```

Если Maven берёт не ту Java (на macOS так бывает из-за старой Java от Oracle),
путь к JDK 21 задаётся явно:

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)
```

### Локальный стенд

Локальный прогон по умолчанию идёт по публичному демо-стенду. Магазин
поднимается и у себя — из готовых образов, без сборки из исходников:

```bash
git clone --depth 1 https://github.com/testsmith-io/practice-software-testing.git
cd practice-software-testing && docker compose -f docker-compose.prod.yml up -d
```

Витрина встанет на `localhost:4200`, API на `localhost:8091`, и прогон
переключается на них:

```bash
./mvnw test -Dbase.url=http://localhost:4200 -Dapi.url=http://localhost:8091
```

Свой `docker-compose.yml` в проекте не лежит намеренно: он повторял бы
официальный, а тот привязан к репозиторию магазина. Ровно эти же команды
выполняет workflow в CI.

## Устройство тестов

**Дефекты закреплены исполняемым кодом.** Восемь найденных дефектов описаны
тестами в `KnownBugsTest`. Каждый проверяет поведение, которого следует
ожидать, и помечен `@KnownBug` со ссылкой на баг-репорт. Пока дефект
воспроизводится, проверка падает и тест засчитывается — прогон остаётся
зелёным. Если дефект исправят, проверка пройдёт, и вот это уронит сборку:
изменение не пройдёт незамеченным.

Приём перенесён из проекта по API 2GIS, где ту же роль играет
`xfail(strict=True)`. В JUnit готового аналога нет: `@Disabled` просто
выключает тест и перестаёт следить за дефектом. Механизм собран
в `KnownBugExtension` и **проверен собственными тестами** — расширение,
которое переворачивает результат, обязано быть проверено, иначе восемь тестов
станут зелёными навсегда и перестанут что-либо означать. Проверить его обычным
тестом нельзя, он и сам попал бы под переворот, поэтому образцы запускаются
отдельным движком JUnit через `EngineTestKit`.

**Параллелизм 2 не означает два браузера.** Прогон разваливался падениями
«элемент не найден», хотя стенд отвечал за доли секунды. Причина нашлась
подсчётом процессов: при заявленных двух потоках работало **24 процесса
chromedriver**. Тесты блокируются на сети, `ForkJoinPool` на каждую блокировку
заводит компенсирующий поток, чтобы удержать заявленный параллелизм, а верхняя
граница пула по умолчанию — `parallelism + 256`. Selenide держит драйвер
на поток, поэтому потоки превращаются в браузеры, и машина захлёбывается.
Помогает `max-pool-size` в `junit-platform.properties`: браузеров стало ровно
два, прогон из четырёхминутного с падениями стал пятидесятисекундным зелёным.

**Ожидание живёт в странице, а не в тесте.** Добавление в корзину асинхронно:
переход на страницу корзины сразу после нажатия обрывал запрос, и корзина
открывалась пустой. Поэтому `addToCart()` сам дожидается роста счётчика
корзины. То же с формой адреса — кнопка перехода включается только после того,
как Angular признает форму валидной, и клик раньше проходит вхолостую. Тест
не должен знать про эти особенности, иначе ожидания расползутся по всему
проекту.

**Готовность витрины определяется по запросам в полёте.** Индикатора загрузки
у магазина нет, адрес при фильтрации не меняется, так что признака «готово»
на странице не найти. Проверка сортировки падала раз в несколько прогонов,
причём на верных данных: API отдавал товары отсортированными, а тест читал
недорисованную сетку.

Первая попытка считать записи Performance API не помогла — у буфера ресурсов
есть предел, после которого новые записи молча отбрасываются, и счётчик
перестаёт расти. Работает другое: на страницу ставится счётчик незавершённых
запросов поверх `XMLHttpRequest`, и сетка считается готовой, когда запросов
в полёте не осталось, а список цен не изменился дважды подряд. Вдобавок
ожидание вызывается после каждого изменения фильтра, а не один раз в конце:
клики подряд отправляют несколько запросов сразу, и выдача более раннего
может прийти последней. Пять прогонов подряд после этого зелёные.

**Страницы не проверяют, тесты не ищут элементы.** Page object выполняет
действия и отдаёт значения, все утверждения лежат в тестах. Поэтому упавший
тест показывает свою строку с `assert`, а не строку внутри страницы. Граница
та же, что между клиентом и тестами в проекте по API 2GIS.

**Состояние готовится через API.** Тесту, которому нужен вошедший
пользователь, незачем заполнять форму из двенадцати полей: это делает его
длинным и роняет по чужой причине. Регистрация проверяется через интерфейс
там, где она сама и есть объект проверки. По той же причине в проекте нет
RestAssured — API здесь инструмент, а не объект тестирования, и DSL для
проверок ответа не нужен. Хватает `HttpClient` из JDK.

**Идентификаторы товаров не зашиты и не кэшируются.** Стенд пересоздаёт базу
и меняет все ULID разом — за время работы над проектом это случилось дважды,
и оба раза страница товара по прежнему идентификатору открылась пустой.
Названия при этом сохраняются, поэтому товар ищется по названию через API.

Кэш идентификатора выглядел очевидной экономией и оказался ловушкой: если
база пересоздаётся посреди прогона, запомненное значение превращается
в ссылку на пустую страницу, и разом падают все тесты, которые открывают
карточку. Лишний запрос к каталогу стоит трети секунды и такой размен
окупает. По той же причине тесты не рассчитывают ни на точное число товаров,
ни на состав списка брендов: создание сущностей открыто без авторизации
(BUG-5), и каталог пополняется чужими записями.

**В CI магазин поднимается свой.** Публичное демо закрыто Cloudflare, и
с адресов GitHub оно отдаёт страницу «Performing security verification»
вместо витрины — браузер до приложения не доходит вовсе. Обходить защиту
от ботов бессмысленно и неправильно, поэтому workflow поднимает магазин
из готовых образов и ходит в `localhost`. Заодно уходят две другие беды
публичного стенда: чужие данные в каталоге и пересоздание базы посреди
прогона, из-за которого один прогон из трёх падал целиком.

**Проверки дефектов умеют отличать дефект от неоткрывшейся страницы.**
Это нашлось на живом примере и стоило переделки механизма. В первом прогоне
CI страницы перехватывал Cloudflare, до магазина тесты не добирались — и все
восемь проверок дефектов позеленели, хотя не проверили ничего: падение
из-за пустой страницы неотличимо от падения из-за дефекта, а расширение
засчитывало любое. Теперь `ElementNotFound` и ошибки драйвера пробрасываются
наружу: элемента нет вовсе — значит, открылось не то, и это не повод
записывать дефект в воспроизведённые. Разделение проверено отдельным тестом.

**Границы проверяются там, где живёт правило.** Предельные длины полей —
серверное правило, форма их даже не ограничивает атрибутом `maxlength`.
Восемь граничных значений через браузер заняли бы полторы минуты и зависели
бы от отрисовки; через API те же восемь проверок отвечают за две секунды.
Через интерфейс проверяется другое — что сообщение об ошибке доходит до
пользователя.

**Инструменты проекта покрыты тестами.** Генератор попарных наборов сокращает
24 сочетания фильтров до 6. Если он потеряет пару значений, вместе с ней тихо
пропадёт покрытие, а прогон останется зелёным, поэтому `PairwiseTest`
проверяет, что все пары на месте и что один и тот же вход даёт один и тот же
набор — упавший тест нужно уметь перезапустить на тех же данных.

**Селекторы держатся на `data-test`.** Это единственный признак, переживающий
пересборку вёрстки: имена классов Angular генерирует заново. Два контрола
магазин оставил без него — вкладка «Continue as Guest» и кнопка удаления
строки из корзины; они ищутся по подписи и по классу, и это единственные
такие места. Заодно замечание для сопровождения: имена не выдержаны в одном
стиле, рядом живут `first-name` через дефис и `postal_code` через
подчёркивание.

**Состояние чистится, браузер не перезапускается.** Старт Chrome стоит около
двух секунд, и на шестидесяти тестах это дороже самого прогона. После каждого
теста чистятся `localStorage`, `sessionStorage` и cookies — корзина магазина
живёт именно в `sessionStorage`. Драйвер у Selenide привязан к потоку,
поэтому параллельным тестам чужое состояние не достаётся.
